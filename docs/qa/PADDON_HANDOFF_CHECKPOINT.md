# W12 active cutting-paddon handoff

Baseline `bbccba57ba8fb2f5a3b7b47499efc64ac431ecd8`; existing isolated branch `codex/web-apparatus-collections-20261014`.

This increment targets server-owned active paddon selection/clear and native successor handoff from an already locked paddon. It does not invoke printing, offline print preparation or print confirmation. Native/backend and mobile remain read-only; no authentication, persistent access or security setting changes are in scope.

| Acceptance scope | Implementation and local verification |
| --- | --- |
| Active selection | GET/PUT `/production-maps/paddons/active`; actor role/ref plus canonical Cut apparatus; native capability and assignment scope; explicit null versus error; choose/clear with fresh selection and target validation. |
| Eligible successor | POST `/paddons/active/next`; actual aparatchi role, queue-manage capability and assigned Cut apparatus; already locked visible source; native source/actor/apparatus successor mapping creates/reuses and activates an open successor. |
| Production effect | Native cutting queue handler attaches active selection inside output transactions. No device code or new completion-body field is needed. New output uses the server's current selection; replays and existing slots do not move old batches. |
| Interrupted/repeated flows | Frozen session RAM intent, double-click guard, scope/unmount abort protection, no automatic application replay, read-only recovery after transport loss; successor creation idempotence is distinguished from its repeated active-pointer side effect. |
| Permissions and UI | Retain existing admin workspace entry; no new access grants. Actual admin role cannot use the operator-only successor endpoint. Empty, loading, denied, malformed and changed-state paths; local desktop/mobile visual review. |

Implemented entry points are `/app/paddons`, active Cut apparatus details and active Cut apparatus queues. The shadcn dialog keeps the selected machine pinned while catalog search changes, distinguishes explicit server `null` from denied/error/loading states, permits direct codes outside the200-row feed, and requires source review and confirmation before operator-only successor handoff. No browser preference or completion-body paddon field replaces the server-owned selection.

The API uses fresh canonical projection, active selection and target/source detail reads before one application dispatch. A changed active baseline or source lock timestamp requires review. Unknown outcomes retain a frozen actor/session-scoped RAM intent after close/remount; recovery reads current state even when the session is offline and never replays the mutation. Observed matching values do not prove the original write succeeded. Repeating `next` explicitly can reselect an existing successor and replace a newer selection from another device.
