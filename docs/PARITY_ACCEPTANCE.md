## Priority findings and constraints

1. **P0 permission acceptance:** the baseline checks `admin.access` at login, but exposes navigation, create forms, settings save, and completion actions without their separate endpoint capabilities. The backend still enforces permission; this finding is a frontend authorization and usability gap, not a demonstrated backend bypass. `admin.access` is not a wildcard for `catalog.item.create`, `party.supplier.manage`, `admin.settings.manage`, or other endpoint requirements. See `W/src/lib/session.tsx:197`, `W/src/pages/ResourcePage.tsx:200,547,764`, `W/src/pages/SystemPages.tsx:175`, and `B/src/http/handlers/admin/system/auth.rs:52`.
2. **P1 existing order, reusable template, and pending order workflows:** baseline lists/details exist, but they do not launch the mobile edit/reuse/complete-pending flows. Calculation edits use the dedicated existing-order edit contract; saved node/edge topology edits use native PUT production-maps. Neither should silently allocate a new order. Pending completion uses `pending_order_id`, preserves the pending order identity, and returns an existing completion on retry. See `B/src/http/handlers/admin/production_maps_order_edit.rs:32`, `B/src/http/handlers/admin/production_maps_pending_order.rs:1`, and `M/lib/src/core/api/admin/mobile_api_admin_production_map_MobileApiAdminProductionMap_methods_01.dart:200`.
3. **P1 production execution:** reading orders and map nodes is not equivalent to mobile queue assignment, reorder, transfer, start/pause/resume, freeze, early close, raw material or mold readiness, WIP intake, output recording, or QR reports. These remain explicit acceptance rows below.
4. **P1/P2 identity discipline:** baseline stock selection already distinguishes `[code, order_id]` (`W/src/pages/ResourcePage.tsx:527`); a same-product/different-order defect is **not** asserted. The backend stock aggregate includes warehouse, order, product, and unit (`B/src/db/postgres_warehouse_impl_parts/part_01.rs:360`); acceptance should use the whole identity. Inventory assets use `kind + asset_ref`, not just `asset_ref` (`B/src/core/inventory_movements_parts/part_01.rs:141`).
5. **P2 bounded lists are not totals:** completed, closed, and completion feeds return at most 200 entries with no offset contract. Workers, warehouses, raw material stock, and opening WIP have bounded snapshot contracts. Infinite scrolling only reveals the retained snapshot; it cannot fetch missing history. The baseline labels bounded resource lists, which should be retained. Stock items are an offset list with a handler cap of 200, while baseline `resourceDefinitions.stock` falls back to a cap of 500. The current resource UI uses pages of 20; callers requesting a page of 200 or more can incorrectly infer exhaustion unless the actual cap and lookahead are respected. See `W/src/lib/api.ts:36,292`, `W/src/lib/resource-list.ts:23`, `B/src/http/handlers/admin/system/warehouses.rs:223`, `B/src/http/handlers/admin/production_maps/completion.rs:379,408,529`.
6. **P2 settings PUT is a complete contract:** the web reads current settings and merges editable fields. Sending `werka_code: ''` does **not** rotate or erase the access code: the backend settings service ignores submitted code fields (`B/src/core/admin/service/mod.rs:223`). Preserve this behavior. A read-before-write merge has no revision precondition, so concurrent settings edits still need an explicit acceptance test and a reported backend limitation if stronger conflict handling is required.
7. **P3 runtime-dependent features:** printer reports, binary images/backup downloads, live sockets, FCM, Telegram QR login, AASX processing, and reset preconditions cannot be certified by TypeScript compilation or demo data. Use controlled local fixtures or an explicitly approved nonproduction service. This task does not authorize executing these server-side operations against production.

## Remaining verification and backend limits

- The audit itself made no backend/mobile changes and executed no server mutations. Source tests cited below are supporting contract evidence, not newly executed tests.
- Backend history and bounded snapshot limitations cannot be removed by frontend infinite scroll. A complete-history requirement is not currently provided by these backend contracts and remains a documented limitation. This task may not change the backend.
- Backend stock pagination orders by display name without the full grouping key (`B/src/db/postgres_warehouse_impl_parts/part_01.rs:361`). Tied names and concurrent inventory changes warrant a controlled pagination fixture; changing backend ordering is forbidden under the strict independent-backend boundary here.
- Warehouse assignment GET exposes only assignment_kind='warehouse' in both Postgres and memory stores (`B/src/db/postgres_warehouse_impl_parts/part_01.rs:104–115`; `B/src/core/warehouses_memory_store.rs:62–73`). Apparatus-to-warehouse maintenance is a documented backend limitation only; ordinary warehouse links can be implemented independently in the web.
- Existing calculation edit, native graph edit, sequence moves, placement updates, inventory transfer, stock and printer operations have different optimistic/idempotence contracts. Native PUT production-maps has no expected revision or command-id field; fresh client preflight cannot remove a concurrent write race between its last read and the server commit. A single generic editor cannot claim to cover them all.
